# 独立客户前端技术设计

状态：已定稿（技术基线），M0 独立工程已建立 · 最近更新：2026-09-27

依据：[需求设计](./需求设计.md) · [页面清单](./页面清单.md) · [视觉基线](./前端设计.md) · [首页与统计修订](./前端设计/首页效果与统计总览修订.md)

用户已接受上一轮技术组合并要求继续。本轮补齐接入边界；[架构设计](./架构设计.md) 与 [独立路线图](./roadmap.md) 按新客户前端分别维护，原项目路线图继续描述既有 Sub2API 业务。

## 1. 技术组合

| 技术 | 用途与推荐理由 | 备选与取舍 |
|---|---|---|
| Next.js + React（统一组织官网和控制台的网页框架） | 官网提供适合搜索收录的页面输出，控制台提供交互；可以直接使用已选定的 Aceternity 组件 | Vite + React 更轻，但官网预渲染与搜索收录需另行安排；本轮推荐 Next.js |
| TypeScript（开发时检查数据和代码是否匹配） | 全工程开启严格模式，减少金额、权限、时间范围等接错字段的问题 | 不采用无严格类型的实现 |
| Tailwind CSS + shadcn/ui（统一样式与常用控件） | 用同一套颜色、间距和尺寸实现按钮、表格、弹层、日历等；适配已确认的灰白黑风格 | 不再并列引入另一套通用控件库 |
| Aceternity UI + Motion（首页动态效果） | 复用已验证可构建的光效和滚动透视组件，控制台只保留必要的交互反馈 | 普通区域用基础样式即可，不为每个区块增加动画依赖 |
| Apache ECharts（绘制统计图） | 绘制环形分布和趋势图；按需加载所用图形，统一分类颜色、提示和空状态 | Recharts 也能完成当前图形；建议选定一套后统一使用 |
| TanStack Query（管理接口请求和结果缓存） | 管理加载、错误、刷新和时间范围切换；查询身份、时间、时区和聚合粒度共同决定缓存归属 | 不另造一套通用请求缓存 |
| pnpm（安装和固定项目依赖） | 新前端维护自己的依赖与锁文件，便于独立构建和升级 | 不与原管理前端共享依赖目录 |

M0 已核对并固定 Next.js 16.3.6、React 19.3.0、TypeScript 5.9.3、Tailwind CSS 4.3.3 与 pnpm 10.34.5；M1 增加 Motion 13.4.4 和服务端模块边界标记。完整版本见 [工程配置](../package.json) 和锁文件。Radix 交互控件配合本项目源码封装，沿用 shadcn/ui 的组合方式。ECharts 和请求缓存库在对应业务阶段加入；当前官网使用服务端公开读取和本地交互状态。早期动效原型的 npm 工程只保留作验证材料。

## 2. 与现有业务的关系

- 账号、组织、权限、余额、密钥、计费、充值订单与用量数据继续由现有 Sub2API 提供。
- 新前端只负责客户界面和必要的数据展示转换，实际扣费、权限判断和充值到账仍以服务端为准。
- 公共模型目录、监控数据与客户统计对接已有接口；本轮时间与监控范围已收敛到现有后端能力。
- 用量查询只选择起止日期，保留按天的常用预选和自定义日期范围；所有查询显式传同一组日期与时区，不新增精确时分参数。
- 登录沿用现有浏览器凭证与请求头协议，客户前端使用独立存储命名，保留同页/跨标签续期协调与服务端退出；私有页面在浏览器确认身份后查询数据。没有引入新的身份系统或数据库。
- 公开状态直接使用现有近 7 天可用率、最近一次响应耗时和近期可用性记录。历史最多 60 个探测点，按实际时间范围展示；首版不提供速度历史或完整七天历史曲线，不扩展后端接口。

## 3. 目录结构

```text
frontend-portal/
  docs/                  需求、设计、路线图和模块文档
  src/
    app/
      page.tsx           官网首页
      catalog/           模型目录
      status/            服务状态
      help/              帮助中心
      design/            默认关闭的内部组件预览
      login/、register/   登录注册（另有密码恢复及第三方回调路由）
      console/           客户控制台；团队页面在 M4 接入
    features/            按账号、模型、用量、余额、密钥、团队拆分
    components/
      ui/                共用基础控件
      layout/            官网导航、控制台侧栏和页面外壳
      charts/            共用图表外观与空状态
      effects/           首页 Aceternity 动效
    lib/
      api/               请求、错误处理和接口数据转换
      time/              时间范围、预选与时区处理
      format/            金额、价格和 Token 展示
    styles/              主题颜色、字号、间距和控件尺寸
  public/                静态素材
```

页面文件主要负责拼装页面，业务规则放进相应功能目录，共用能力再下沉到公共目录。官网与控制台复用主题和基础控件，各自保留适合任务的布局。

## 4. 部署结构

- 新前端独立构建和发布，建议以独立 Node.js 服务运行；具体承载环境在部署设计中确定。
- 面向客户使用一个网站域名，由入口代理把网页请求交给新前端，把业务请求交给现有 Sub2API。这样便于集中处理登录和接口访问。
- 原平台管理界面保留自己的访问入口；新前端构建不覆盖原 Go 服务中嵌入的管理界面。
- 原管理界面建议使用独立管理域名；已有模型调用、兼容入口和支付通知直接到 Go。模型目录使用 `/catalog`，为已有模型 API 保留 `/models`。具体路径和待验项见 [接入核对](./调研/2026-09-26-接入契约核对.md)。
- 接口转发仅面向固定的业务后端，价格和公开状态可按实际更新频率缓存；账号、余额与个人用量不得进入共享的公开缓存。
- 本文件只提出部署结构，没有创建服务、修改域名或发布站点。

## 5. 工程规范与验证

- TypeScript 开启严格模式；接口返回值在边界检查，金额和未知价格沿用既有业务精度与语义。
- 仓库已补齐新前端样式和配置文件的换行规则；采用 Prettier、ESLint、TypeScript、Vitest 和框架构建，合并为 `pnpm check`。离线预览使用 `pnpm preview:offline` 生成单文件，不启动服务。
- 为时间范围计算、费用展示规则、权限相关状态和接口数据转换等核心逻辑编写有业务意义的测试。
- 主题、配色、布局与组件外观不写单元测试，使用实际页面截图和交互检查验收。
- 对登录、创建密钥、查看消费、充值订单等关键流程安排联调；样例数据只用于设计和隔离开发，真实页面必须明确处理加载、错误与空数据。
- 未经用户明确要求，不启动开发或预览服务器。

## 6. 本批讨论后的顺序

1. 收敛技术设计，明确依赖、目录和部署方式。
2. 写架构设计：页面如何调用后端、登录如何工作、各业务模块如何分工。
3. 排独立前端路线图，并为各里程碑建立对应模块文档入口。
4. 开发先完成主题与基础组件，再实现页面和业务接入；按天用量查询与首版状态监控纳入对应里程碑，复用现有接口。

技术组合、架构与 M0–M5 顺序已作为实施基线。M0 独立工程已交付，M1 官网四页与公开接口读取已实现；两阶段仍需浏览器验收，M1 还需真实后端联调。

## 7. 关键决策

| 决策 | 理由 |
|---|---|
| 公开页面服务端输出，私有控制台在浏览器恢复身份后取数 | 兼顾公开内容阅读与现有请求头认证，不新增身份中转系统 |
| 独立前端工程与独立发布 | 原管理界面可继续工作，新界面可独立升级与回退 |
| 固定后端转发，模型调用直达 Go | 保持现有流式与长连接能力，网页服务只承担网页职责 |
| 用量按天查询，状态历史只展示近期可用性 | 用户于 2026-09-27 明确简化；这两项直接复用已有接口，取消对应后端扩展 |
| 架构与模块文档标注规划和实际实现 | 设计确认不代表已完成运行验收 |
