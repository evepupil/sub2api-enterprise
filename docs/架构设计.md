# Sub2API Enterprise 架构设计

版本：0.3.0

更新日期：2026-10-03

阶段：M1 架构设计确认稿，功能尚未实现

关联需求：[需求设计](./需求设计.md)

项目路线图：[roadmap](./roadmap.md)

## 1. 架构目标

在现有 Sub2API 中增加组织能力，让个人用户和组织用户共用同一套注册、密钥、模型调用、计费和用量系统。

M1 保持现有单体部署，不增加独立服务。组织能力作为新的内部业务模块，与现有模块协作。

## 2. 系统边界

Sub2API 继续负责：

- 用户注册、登录和平台身份。
- 组织、成员、邀请码和成员配额。
- API 密钥及分组权限。
- 模型请求转发、计费和使用记录。
- 平台管理员与组织管理员的控制台能力。

模型供应商仍是系统外部依赖。M1 不接入 ACF 和 ManyRouter，也不改变现有模型转发职责。

## 3. 系统概览

```mermaid
flowchart TB
    U[个人用户与组织成员] --> F[现有 Web 控制台]
    PA[平台管理员] --> F
    F --> A[接口与身份校验层]
    K[API 密钥调用方] --> A

    A --> O[组织业务模块]
    A --> C[现有核心业务]

    O --> C
    C --> G[模型网关]
    G --> P[外部模型供应商]

    O --> DB[(PostgreSQL)]
    C --> DB
    O --> R[(Redis)]
    C --> R
```

组织业务模块只处理组织相关规则。模型转发、价格计算和供应商调度继续由现有核心业务负责。

## 4. 架构分层

| 分层 | 职责 |
|---|---|
| 前端展示层 | 注册、组织成员管理、组织用量和平台组织管理；复用现有页面框架和组件 |
| 接口与身份校验层 | 识别当前用户或 API 密钥，校验平台管理员、组织管理员和普通成员的访问范围 |
| 业务层 | 处理注册、组织、成员、分组、密钥、结算和用量规则 |
| 数据访问层 | 统一读写组织、用户、密钥、余额和使用记录，保证关键操作的一致性 |
| 基础设施层 | PostgreSQL 保存业务事实，Redis提供缓存和快速额度检查，现有网关连接外部模型 |

各层继续遵循仓库现有依赖方向：上层调用下层，业务规则不放进前端或数据库访问代码。

## 5. 业务模块关系

### 5.1 组织模块

组织模块负责组织、成员关系、组织邀请码、成员配额和组织分组范围。它向其他模块提供当前用户的组织身份、付款归属和可用分组。

当前模块设计：[组织身份与注册](./模块设计/组织身份与注册.md)

### 5.2 注册模块

注册模块继续负责所有注册入口和现有校验。完成注册时调用组织模块，形成个人用户、组织创建者或组织普通成员。

用户、组织关系和邀请码状态需要一起成功或一起失败。

### 5.3 密钥与分组模块

密钥仍归创建密钥的用户。个人用户沿用现有分组规则；组织用户使用平台授予该组织的分组。

密钥创建和每次调用都检查组织分组，保证授权收回后已有密钥也无法继续使用该分组。

### 5.4 计费模块

计费模块继续使用现有价格和用量计算。个人调用由本人付款；组织普通成员调用由组织创建者付款，同时累计该成员的消费配额。

组织创建者自己的调用由本人付款，用量归本人。成员使用自己的密钥时，用量归成员。

### 5.5 使用记录模块

使用记录继续保存每次调用。组织管理员可以查看本组织范围，普通成员只能查看自己，平台管理员保持全平台权限。

组织统计在现有筛选和统计能力上增加组织范围与成员分布。

## 6. 主要业务流程

### 6.1 注册

```mermaid
flowchart LR
    A[提交注册] --> B[现有注册校验]
    B --> C{注册类型}
    C -->|个人| D[创建个人用户]
    C -->|创建组织| E[创建用户和组织]
    C -->|组织邀请| F[创建用户并加入组织]
    D --> G[完成登录]
    E --> G
    F --> G
```

开放注册和邀请码开关对所有注册入口保持一致。

### 6.2 API 调用与结算

```mermaid
flowchart LR
    A[验证 API 密钥] --> B[检查用户与组织权限]
    B --> C[检查分组、余额和配额]
    C --> D[调用外部模型]
    D --> E[按实际用量结算]
    E --> F[写入使用记录]
```

成员、付款账号、密钥和组织归属在一次调用中保持明确。关键结算沿用现有幂等处理，避免请求重试导致重复扣费。

### 6.3 组织管理

平台管理员设置组织可用分组并查看全平台组织。组织管理员只管理自己的成员、邀请码和配额。所有组织范围都由服务端根据当前身份确定。

## 7. 数据与一致性原则

- PostgreSQL 是组织关系、权限、余额、配额和使用记录的业务依据。
- Redis只提升读取和额度检查速度，不能单独决定永久权限或余额。
- 注册和消费结算属于关键事务，相关数据需要一起提交。
- 权限或配额修改先写入数据库，再更新或清理缓存。
- 历史用量保存调用发生时的组织归属，成员停用不会改变历史记录。
- 现有个人用户没有组织关系，升级后继续执行原有业务。

## 8. 权限架构

平台权限与组织权限分开判断：

- 平台管理员可以管理全平台用户、组织和分组授权。
- 组织管理员只拥有本组织的成员、邀请码、配额和用量管理权限。
- 普通组织成员管理自己的密钥并查看自己的用量。
- 个人用户保持原有能力。

前端只负责展示可用入口。后端对每次读取和修改重新校验范围，防止通过修改请求访问其他组织。

## 9. 运行与故障边界

- 对外运营使用默认完整运行模式，组织注册、管理和计费都在该模式工作。
- 数据库不可用时，涉及组织权限或结算的请求停止处理，避免产生无法确认的归属和费用。
- 缓存异常沿用现有降级和告警能力，不能放宽组织权限。
- 外部模型调用继续使用现有超时、重试和错误处理规则。
- 组织功能发布不要求迁移现有个人用户，也不影响已有个人密钥。

## 10. 后续阶段衔接

- M2 只调整整体视觉和控制台体验，继续使用 M1 的组织业务边界。
- M3 将 ACF 接入接口与身份校验边界，不进入组织结算核心。
- M4 将 ManyRouter 接入模型供应和线路管理边界，不接管用户、组织、余额和使用记录。

各阶段开始前再讨论对应模块，并编写模块设计文档。

## 11. M1 架构边界

M1 保持单组织、单组织管理员和统一付款账号。暂不提供多组织身份、部门、项目层级、成员迁移、组织解散、管理员转让、ACF 接入和 ManyRouter 接入。

## 12. 客户官网架构（M5）

<a id="layer-portal"></a>

客户官网 `frontend-portal/` 是独立的 Next.js 应用，本轮只有界面，不调用后端。分五层，上层只依赖下层：

| 层 | 目录 | 职责 |
|---|---|---|
| 页面层 | `src/app/[locale]/(site)`、`(auth)` | 按路由组合区块、生成页面标题；`(site)` 带顶栏页脚，`(auth)` 不带 |
| 区块层 | `src/blocks/<页面>/` | 每个区块自成一体、不收参数，自己读数据与网址状态 |
| 共享界面层 | `src/components/{ui,layout,effects,catalog}` | 按钮、分段控件、顶栏页脚、网格光线、跑马灯、地球、厂商标志、分组倍率徽标等 |
| 数据与状态层 | `src/lib/` | 模型目录、通道（即分组）、价格换算、筛选排序、可用率（占位数据 + 纯函数 + 单测）；网址状态钩子 |
| 多语言层 | `src/i18n/`、`src/messages/` | 语言路由、按请求加载文案 |

数据流：页面在服务端读后台模型广场 → 数据层纯函数整理成「每个分组里的每个模型」一条、价格按所在分组的倍率算 → 区块用 `useCurrency()` 等读网址里的币种与筛选条件 → 格式化后渲染。2026-10-06 起官网按分组展示：「通道」只是对外的说法（通道页并排三种通道、只比权益），模型页、价格页不做通道切换，同一个模型在几个分组里就列几个价格（企业通道按合同定价，不出单价；倍率只参与换算，官网页面不展示）。

后续对接后端时，只把数据层的占位数据换成接口适配（模型与价格、通道与分组倍率、可用率监测），函数签名保持不变，区块不用改；登录注册接入现有账号接口（个人注册、创建组织、组织邀请码），控制台另立模块。

## 13. 客户控制台架构（M6）

<a id="layer-console"></a>

客户控制台和官网同一个应用（`frontend-portal/`），沿用第 12 章的分层，多出一层控制台外壳：

| 层 | 目录 | 职责 |
|---|---|---|
| 页面层 | `src/app/[locale]/console/<页>/page.tsx` | 登记语言、给页面标题，内容交给区块；`/console` 跳到用量页 |
| 外壳层 | `src/app/[locale]/console/layout.tsx`、`src/components/console/shell/` | 公告条、侧边栏（可收起、手机端抽屉）、头像菜单、通知；只给浏览器控制台自己的文案 |
| 区块层 | `src/blocks/console/<页>/` | 每页一个客户端区块，筛选条件和编辑状态都在页内 |
| 共享界面层 | `src/components/console/` | 页面骨架、面板、数字卡、筛选下拉、日期范围、表格与分页、弹窗与抽屉、开关、复制、柱状图、热力图 |
| 数据与状态层 | `src/lib/console/` | 用量、日志、密钥、流水、邀请、组织、对话的占位数据与纯函数（单测锁住）；时间统一按北京时间，「现在」固定 |

数据流：区块用本地状态保存筛选条件 → 调数据层的纯函数筛选、汇总、分页 → 格式化后渲染；新增、编辑、删除只改页内的副本。价格沿用官网的「官方价 × 分组倍率」。

文案分组下发：官网页面只把官网的命名空间交给浏览器，控制台布局换成控制台的命名空间（嵌套的文案上下文整体替换、不合并，所以控制台这组也带上公共的 common）。

后续对接后端：数据层换成接口适配（用量统计、请求日志、密钥、钱包流水、返利、组织成员），函数签名不变；区块把「改本地副本」换成「调接口后重新取数」。
