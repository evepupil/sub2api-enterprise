# ACF 身份解析接口模块设计

模块定位：给 ACF 安全网关提供「密钥换归属」的内部接口——拿一把原始调用密钥，返回组织、用户、密钥三级标识与名字，让 ACF 能把每条 AI 请求对应到具体的人和密钥。

## 1. 职责与边界

本模块负责：

- 回答「这把密钥是谁的」：组织、用户、密钥三级编号与名字。
- 校验调用方的服务凭证，拒绝未鉴权调用。
- 对解析请求做轻量限流与请求体限制。

本模块不负责：

- 判断密钥还能不能用。有效性由正常鉴权链路决定，这里只答归属；因此停用密钥、停用账号照样返回归属。
- 主动推送密钥或人员变更。ACF 一次绑定永不变更，注销、离职、改名都不跟进。
- 组织、成员、密钥的管理操作。

## 2. 结构与数据流

```
ACF 网关 ──POST /api/internal/identity/resolve──> 凭证中间件 ──> 限流 ──> 请求体限制 ──> 解析接口
                                                                                  │
                                                       密钥仓储 GetByKey（含属主）──┤
                                                       组织服务 GetSummaryByUserID ─┘
                                                                                  │
                                                            200 归属 / 404 key_not_found
```

- 路由组挂在引擎根上，与面板、模型网关完全分开；服务凭证未配置时整组不注册。
- 查询路径：按原始密钥查密钥表（唯一索引，软删除过滤，随查询带出属主账号），再按用户查组织归属。无缓存依赖，单次请求三笔小查询。

## 3. 关键决策

按 2026-09-17 与需求方的逐条讨论定稿：

| 决策 | 结论 | 理由 |
| --- | --- | --- |
| 个人用户的归属 | 组织一层返回 `null`，空即个人用户（对 ACF 原契约的修改提案） | 原契约要求组织必填；个人用户没有组织。伪组织方案可用但把展示诉求焊进永久存储的标识里；「空即个人」语义诚实、实现更少，ACF 只需在适配层收下空组织。若 ACF 评估后收不了，退回「一人编一个组织」方案，一个配置开关的事 |
| 空组织的请求怎么处置 | 写进契约提案：沿用 ACF「归属未知」的既有规则——只观察、不改流量 | ACF 的策略按组织生效，没有组织就没有策略来源；沿用既有规则避免新增「无组织策略」概念 |
| 编号格式 | 平台内唯一 ID 原样返回，以字符串形态传输（JSON number 会让对方解析失败） | 编号职责只有「稳定不变、两边对账」；自增主键、删除只打标记，天然满足永不变更。前缀方案已评审否决：显示靠名字，对账靠列名 |
| 名字取值 | 用户名按「成员备注名 > 用户名 > 邮箱」，组织名取当前组织名，密钥名取备注名；名字一定返回 | ACF 界面和告警显示的是名字，不是编号；名字必给直接决定对方产品可不可用 |
| 名字快照 | ACF 存第一次解析时的名字，之后改名不跟进 | 审计要的是事发当时的名字；新密钥解析自然带新名字；真要对账拿编号人工查。不做同步机制 |
| 停用密钥/账号 | 照常返回归属 | 归属和有效性是两件事；查无（不存在、已删除）才 404，契约约定「格式不对」也归 404 |
| 凭证形态 | Bearer 固定令牌，环境配置（`acf.identity_credential` / `ACF_IDENTITY_CREDENTIAL`），常数时间比较 | 服务间秘密，与 JWT 密钥同级，不进数据库不进界面；未配置时整组接口不注册，绝不留不设防的入口 |
| 限流 | 进程内固定速率（20/秒，突发 40），超限 429 | 正常流量约等于新密钥出现频率，离阈值很远；闸门是防凭证泄露后的密钥枚举 |

## 4. 当前实现

- 用例层：`IdentityResolutionService.Resolve`——查密钥与属主，查组织归属，拼三级归属；个人用户组织为空。两个依赖收窄成专属小接口，由 wire 绑定到密钥仓储和组织服务。
- 接口层：`IdentityResolutionHandler.Resolve`——校验请求体，映射契约 JSON（编号转字符串、组织可空、错误码 `key_not_found` / `invalid_request`）。
- 中间件：凭证认证（SHA-256 摘要常数时间比较，未配置 503、不对 401）、进程内限流（429）、请求体限制（8KB）。
- 配置：`acf.identity_credential`，支持配置文件与 `ACF_IDENTITY_CREDENTIAL` 环境变量；默认留空（接口关闭），默认值显式注册保证纯环境变量部署可达。
- 组织服务与组织仓储补齐了成员备注名的读取链路（`OrganizationSummary.DisplayName`），组织页现有调用不受影响。

## 5. 验证方式

- 用例单测（无需数据库）：成员优先备注名、备注缺失回退用户名/邮箱、个人用户组织为空、查无此密钥、停用密钥照样归属、同人多密钥同编号、仓储故障不伪装成 404。
- 接口单测：200 契约形状（编号为字符串）、个人用户 organization 为 JSON null（存在且为 null）、404 契约体、超长密钥按 404、坏请求 400。
- 中间件单测：缺头/非 Bearer/错凭证 401、正确 200、未配置 503、超出突发额度 429（注入零补充速率做确定性验证）。
- 契约回执集成测试（连真实数据库，`-tags=integration`）：测试扮演 ACF 客户端按契约发请求，覆盖成员归属、停用密钥、个人用户 null 组织、查无 404、软删除 404、凭证强制、坏请求 400；与 ACF 仓库里按契约实现的「假 Sub2API」互为镜像。
- 门禁：`go build`、`go test ./...`、`golangci-lint run ./...` 全绿（2026-09-17）。集成测试在本机 Windows 侧因 Docker 不可用自跳过，随部署后联调人工执行。
- 真实联调（2026-09-17，ACF 侧以与 acf-gateway 完全相同的装配执行：真实网关处理器 + 真实库 + 真实本服务）：四条用例全过——组织成员密钥三层归属落库且组织名逐字节一致；个人用户密钥落「个人用户」桶、用户归属不丢；错误凭证与查无密钥均故障放行、归属不落库。两则联调备忘：ACF 网关默认也监听 :8080，同机对跑需设 `ACF_GATEWAY_ADDR` 错开；本服务日志中同一密钥出现多条 resolve 记录属预期——联调方每次新建端点（缓存键是「端点+指纹」）或直接 curl 验证都会触发，稳态下 ACF 对同一把密钥只问一次。

## 6. 待扩展项

- 名字陈旧若成为痛点：ACF 侧引入用户表定期同步，或在后续组织只读接口（对方 M8）中捎带名字查询。首期不做。
- 组织级只读接口（ACF 对方 M8 的插件数据来源）：属 M3 后续模块，另行设计。
- 本机部署形态收敛：8080 跑的是 `bin/server-identity.exe`（旧 `bin/server.exe` 被 18080 端口的旧实例锁定无法覆盖），确认旧实例弃用后重建统一。
