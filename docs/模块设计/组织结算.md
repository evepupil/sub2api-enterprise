# 组织结算模块设计

模块定位：让组织普通成员花的钱从组织付款账号出，并把成员的消费上限在调用前真正管起来。

## 1. 职责与边界

本模块负责：

- 组织普通成员的每一次消费，从组织付款账号（组织创建者）的余额里扣，同时累计这个成员的已消费金额。
- 调用前把两件事一起拦住：组织付款账号有没有钱、这个成员自己的上限还剩多少。
- 批量出图这类需要先冻结再结算的业务，冻的是组织付款账号的钱，同时占住成员的额度。
- 余额不足的通知发给组织付款账号本人。

本模块暂不负责：

- 组织充值。组织管理员照现有充值流程给自己的账号充钱，资金就在他的账号余额上。
- 组织维度的用量统计和成员分布，由[组织用量与平台管理](./组织用量与平台管理.md)实现。
- 成员上限的设定和均分，由[成员管理与消费配额](./成员管理与消费配额.md)负责，本模块只让它生效。

## 2. 现有实现基础

- 扣费已经集中在一笔数据库事务里完成，带请求幂等键，重试不会重复扣。
- 调用前有一套资格检查：余额走缓存读取，花完同步累加，订阅和各类限额也在这里判断。
- 批量出图已经有「提交时冻结、结算时按真实花费扣、取消时全额退回」的三条路径。
- 鉴权快照把账号信息缓存起来，调用链不用每个请求查库。

本模块沿用这些机制，只把「钱记在谁头上」和「成员额度」接进去。

## 3. 付款归属

谁付钱在扣费事务里现算，不从请求上下文带进来：

| 调用者 | 扣谁的余额 | 累计谁的已消费金额 |
|---|---|---|
| 个人用户 | 本人 | 不累计 |
| 组织管理员 | 本人 | 不累计 |
| 组织普通成员 | 组织管理员 | 该成员 |

放在事务里现算的原因：付款归属和扣款必须是同一时刻的事实，缓存里的旧归属会把钱扣到错误的账号上。

同一个成员的多把密钥共用一份已消费金额，所以多密钥自然受同一个上限约束。

## 4. 调用前的两道闸

鉴权层还有一道更早的余额闸（余额为 0 直接 403）。组织普通成员自己没有余额，这道闸必须看组织付款账号，否则成员的每一次调用都会在进入计费判断之前被误拒。付款账号的余额随鉴权快照缓存，付款账号充值或状态变化时，连同全体成员的鉴权缓存一起清掉，新的余额立刻生效。


第一道看钱：余额按付款账号查，组织成员查的是组织管理员的余额。

第二道看额度：成员的配额分两种执行模式，判断前先按当前时刻解析生效模式——配了周期配额且已生效的，上限取「每期金额加本期一次性加成」，已消费按当期累计；没配周期或锚点还在未来的，按静态上限执行（留空不限额、0 禁止）。本期一次性加成来自[配额申请制](./成员管理与消费配额.md#7b-配额申请制)，换期清零，不改每期金额。周期模式的解析与推进规则见[成员管理与消费配额](./成员管理与消费配额.md#7a-周期怎么自动恢复惰性推进)。调用热路径不读申请表。

两道都过不了时给的提示不一样，也都不会把组织账户的金额告诉成员：

| 情况 | 成员看到的提示 |
|---|---|
| 自己的上限用完 | 你的消费上限已用完，请联系组织管理员 |
| 组织付款账号没钱 | 组织余额不足，请联系组织管理员 |

个人用户的提示和行为一点不变。

## 5. 预扣业务

批量出图提交任务时：

1. 先按成员的生效上限判断这笔预扣放不放行，判断时锁住成员这一行，让同一成员的并发提交排队，避免各自看到旧数字后一起冻结、加起来超过上限；行锁内先做周期推进（该换期了就把当期起点推进、当期已消费清零、本期一次性加成清零），再比较。
2. 冻结组织付款账号的余额，同时在成员身上占住同样的金额。
3. 结算时按真实花费累计成员已消费金额，多冻的部分连同成员那边的占用一起释放。
4. 取消时全额退回，成员的已消费金额不变。

成员的剩余额度因此等于「生效上限减已消费减已冻结」。周期生效中的生效上限是每期金额加本期一次性加成。周期推进时冻结金额不清，带进新期继续占用新期额度；一次性加成清零，不带进新期。

## 6. 缓存与一致性

- 成员已占用的额度（已消费加已冻结）和余额用同一套办法：调用前读缓存，扣完同步累加，让下一次调用立刻看到。并发请求同时在跑时可能略微超出上限，这一点和现有余额的行为一致。
- 缓存未命中时回源数据库并异步建缓存；回源查询在行锁内先做周期推进，保证建进缓存的数字属于当前期；读取失败按服务不可用处理，不放行。
- 周期模式的已占用额度缓存把 TTL 截到本期截止时间：换期那一刻缓存最多还活几秒，到期自动回源重建，成员不会因为旧缓存多等一个周期。缓存没过期但已换期的极端时序下，旧值只会偏大（把成员多拦一阵），方向安全。
- 生效上限跟随鉴权快照缓存。周期到期恢复不改变金额，快照不用重建；「未来锚点到点生效」这一种切换在快照 TTL 内可能仍按旧上限执行，与既有「改上限清缓存加 TTL」的口径一致，由预扣路径的数据库行锁判断兜底。
- 预扣产生的冻结只写数据库，缓存最多晚一个缓存周期反映出来。数据库侧的预扣判断是权威的，所以超出上限的预扣一定会被拒。
- 成员的消费上限跟着鉴权快照缓存，改完上限立刻清掉该成员的鉴权缓存。
- 鉴权快照版本号上调，升级后旧快照作废重建，避免升级前缓存的快照绕过新的判断。

## 7. 权限与安全

- 付款归属完全由服务端在事务里查出来，请求里带什么都不影响。
- 成员看不到组织付款账号的余额，错误提示只说明该找谁。
- 组织管理员的密钥继续挂在他自己名下，用量也记在他本人名下，交给别人用不改变归属。

## 8. 当前实现

- 成员关系表增加「已冻结金额」列并提供幂等迁移，剩余额度改为「上限减已消费减已冻结」。
- 扣费事务里新增付款归属解析：查到组织且自己不是创建者时，扣创建者的余额并累计自己的已消费金额，扣费结果里带回付款账号和成员标识。
- 调用前的资格检查按付款账号查余额，并新增成员额度判断；组织口径的两种提示分别返回。
- 批量出图的冻结、结算、取消三条路径都走付款账号，冻结前先过成员上限。
- 扣费后余额缓存按付款账号更新，成员已占用额度同步累加；余额不足通知读取付款账号本人的通知设置。
- 成员消费上限改动后清理该成员的鉴权缓存。
- 鉴权层的余额闸改看付款账号，组织成员余额不足时返回组织口径提示；付款账号的余额随鉴权快照缓存，组织创建者的缓存失效会连带清掉全体成员的缓存。
- 组织成员列表在剩余额度下方显示当前冻结金额，冻结为 0 时不显示。
- 周期生效上限已统一为「每期金额加本期一次性加成」（配额申请批准后补当期）：额度闸、预扣的数据库判断、缓存回源推进、鉴权快照、成员列表全部一致；换期、取消或改配周期、写静态上限与均分都会清加成，发放后清成员鉴权缓存。申请表不进热路径。
- 周期配额接入（2026-09-15）：额度闸、扣费累计与预扣全部经 `ResolveMemberQuotaState` 解析生效模式——周期生效中上限取每期金额，其余沿用静态；预扣与缓存回源在行锁内先做周期推进（当期起点对齐、当期已消费清零、冻结带进新期）；鉴权快照按构建时刻解析生效上限，每期金额跨期不变，换期不需重建快照。
- 已占用额度缓存的累加脚本改为保留原存活期（KEEPTTL），回源建键时把 TTL 截到本期截止：换期那一刻缓存准时过期回源推进，成员不会因旧缓存多等一个周期。

## 9. 验证方式

### 9.1 核心业务测试

- 成员消费扣组织管理员余额，成员自己的余额不变，金额同时累计到成员已消费。
- 组织管理员自己的调用扣自己的余额，不占成员额度。
- 组织付款账号没钱时返回组织口径提示，且不暴露金额。
- 成员上限为 0、已用顶到上限、已用加冻结顶到上限时都被拒绝；不限额的成员不受影响。
- 批量出图提交时冻结管理员余额并占住成员额度，结算按真实花费累计、取消全额退回。
- 预扣金额超过成员上限时直接拒绝，钱和额度都不动。
- 个人用户的扣费、提示和通知行为保持不变。

## 10. 决策记录

| 决策 | 结论 | 说明 |
|---|---|---|
| 成员额度的实时判断 | 和余额一样走缓存计数 | 热路径不额外查库；代价是并发请求可能略微超出上限，与现有余额行为一致 |
| 报错口径 | 额度用完和组织没钱分开提示，都不报金额 | 成员知道该找谁，又看不到组织账户情况 |
| 预扣业务 | 一起支持，冻组织管理员的钱 | 成员的批量出图功能不缺口，剩余额度按「上限减已消费减已冻结」算 |
| 付款归属在哪算 | 扣费事务里现算 | 付款归属和扣款是同一时刻的事实，避免缓存里的旧归属把钱扣错账号 |

## 11. 待扩展项

- 统一扣费仓储缺席时的降级路径只保证扣对账号，不累计成员已消费金额。该路径只在测试或降级时运行，正式部署不会走到。
- 预扣产生的冻结在缓存里最多晚一个缓存周期反映，数据库侧判断是权威的。
- 组织维度用量统计与成员分布，由[组织用量与平台管理](./组织用量与平台管理.md)实现。
- 配额申请制落地时额度闸与预扣的生效上限改为「每期金额加本期一次性加成」——已实现，换期与取消周期时清加成，申请表不进热路径。设计见[成员管理与消费配额](./成员管理与消费配额.md#7b-配额申请制)。
